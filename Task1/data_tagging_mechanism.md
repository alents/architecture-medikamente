# Механизм тегирования данных — «Медикаменте»

## 1. Каталог тегов

### 1.1. Теги классификации данных

Определяют категорию данных и уровень конфиденциальности.

| Тег | Описание | Пример полей |
|-----|----------|-------------|
| `PII` | Персональная идентифицирующая информация | ФИО, дата рождения, телефон, email, адрес |
| `PHI` | Медицинская информация (Protected Health Information) | Диагнозы, хронические заболевания, медицинские заключения |
| `CLINICAL` | Клинические данные | Результаты анализов, лабораторные показатели |
| `FINANCIAL` | Финансовые данные пациента | Платежи за услуги, данные договора |
| `PUBLIC` | Общедоступные данные | Название услуги, расписание специалистов, адрес филиала |

### 1.2. Теги жизненного цикла данных (Data Lineage)

Отслеживают состояние и этап обработки данных.

| Тег | Описание | Пример применения |
|-----|----------|-------------------|
| `RAW` | Сырые данные, поступившие из источника | Результаты анализов из лаборатории (`raw_lab_results`) |
| `VERIFIED` | Данные прошли верификацию | Результаты анализов после проверки врачом (`verified_lab_results`) |
| `ANALYTICS` | Данные подготовлены для аналитики | Обезличенные показатели в озере данных (`lab_analytics`) |
| `ARCHIVE` | Данные подлежат архивации | Записи пациентов старше установленного срока |
| `PENDING_DELETION` | Данные ожидают удаления | Данные пациента, отозвавшего согласие на обработку |
| `DEPRECATED` | Данные признаны избыточными и подлежат удалению | Ранее собранные сведения о месте работы/учёбы (принцип минимизации) |

### 1.3. Теги способа защиты

Определяют, какой механизм защиты должен применяться к данным.

| Тег | Описание | Автоматическое действие |
|-----|----------|------------------------|
| `ENCRYPT` | Данные подлежат шифрованию at rest и in transit | Автоматическое шифрование при записи в хранилище |
| `TOKENIZE` | Данные подлежат токенизации | Замена на токен, оригинал — в зашифрованном хранилище ПДн |
| `MASK` | Данные подлежат маскированию при отображении | Применение маски в UI (`+7 (***) ***-45-67`) |
| `OBFUSCATE` | Данные подлежат необратимой обфускации | Необратимое искажение (для избыточных данных) |

## 3. Правила работы тегов

### 3.1. Автоматические действия на основе тегов

| Условие | Действие |
|---------|----------|
| Данные получают тег `ENCRYPT` | Автоматическое шифрование при записи в хранилище (ключи — в StarVault) |
| Данные получают тег `TOKENIZE` | Замена значения на токен; оригинал шифруется и сохраняется в зашифрованном хранилище ПДн |
| Данные получают тег `MASK` | При отображении в UI применяется маска; полное значение — по явному действию пользователя с логированием |
| Данные получают тег `OBFUSCATE` | Необратимое искажение данных |
| Данные получают тег `PENDING_DELETION` | Запуск процесса удаления с уведомлением ответственного |
| Данные получают тег `DEPRECATED` | Запуск процесса необратимого удаления ранее собранных данных. Новые данные этого типа не принимаются |
| Данные получают тег `ARCHIVE` и возраст превышает установленный срок | Автоматическое перемещение в защищённое архивное хранилище |
| Сырые данные с тегом `RAW` хранятся дольше 30 дней без перехода в `VERIFIED` | Уведомление ответственного сотрудника |

### 3.2. Контроль доступа

Доступ к данным определяется связкой двух компонентов:
- **IAM-система (Keycloak)** — хранит пользователей и их роли. При аутентификации выдаёт JWT-токен с указанием роли (например, `role: doctor`).
- **Система управления метаданными (OpenMetadata)** — хранит каталог данных, теги классификации и политики доступа: какая роль имеет доступ к данным с какими тегами.

Приложение при запросе данных получает роль из JWT, обращается к политикам и решает, какие данные показать.

| Роль | Доступные теги классификации | Ограничения |
|----------------|------------------------------|-------------|
| Doctor | `PII`, `PHI`, `CLINICAL` | Доступ к `FINANCIAL` и `ANALYTICS` закрыт |
| Reception | `PII` | Доступ к `PHI`, `CLINICAL`, `FINANCIAL` закрыт |
| Cashier | `FINANCIAL`, `PII` (только номер договора и ФИО для печати платёжного документа) | Доступ к `PHI`, `CLINICAL` закрыт. Может принять платёж и распечатать платёжный документ |
| Bookkeeper | `FINANCIAL` | Доступ к `PII` (кроме номера договора), `PHI`, `CLINICAL` закрыт |
| Patient | `PII`, `PHI`, `CLINICAL`, `FINANCIAL` | Только собственные данные |
| Analyst | `ANALYTICS` | Доступ к `PII`, `PHI`, `CLINICAL`, `FINANCIAL` в необезличенном виде закрыт |

При добавлении новых данных достаточно присвоить им тег классификации — доступ определится автоматически через политику. Не нужно прописывать права для каждого сотрудника отдельно.

### 3.3. Валидация релизов

Как указано в финальном состоянии кейса, релизы проверяются в автоматическом режиме на работу с тегированными данными:

| Проверка | Описание |
|----------|----------|
| Запрет на вывод данных с тегом `PII`/`PHI`/`CLINICAL`/`FINANCIAL` в логи | CI/CD pipeline сканирует код на наличие логирования тегированных полей |
| Проверка наличия тега `ENCRYPT` у новых полей с медицинскими данными | Автоматическая проверка схемы БД при миграциях |
| Проверка доступа к тегированным данным через хранилище ПДн | Тесты подтверждают, что прямого доступа к оригиналам токенизированных данных нет |
| Проверка отсутствия захардкоженных секретов | SonarQube сканирует код на наличие ключей, паролей, токенов |

## 4. Выбор инструментов

### 4.1. Контекст компании

- IT-команда: 3 человека (технический директор, сетевой администратор, бизнес-аналитик), планируется расширение.
- Стек: Java, Postgres, ClickHouse, Elastic, Kubernetes, Victoria Metrics.
- Инфраструктура: локальная, планируется масштабирование на филиалы.

## 5. Обеспечение конфиденциальности данных в потоках

### 5.1. Идентификация потоков данных

На основании кейса и ландшафта компании выделены следующие потоки данных, в которых участвуют конфиденциальные данные пациентов:

| # | Поток данных | Участники | Данные в потоке |
|---|-------------|-----------|-----------------|
| П1 | Регистрация пациента | Пациент → Ресепшен → Система | ФИО, дата рождения, телефон, email, адрес |
| П2 | Запись к специалисту | Пациент (через ЛК/портал) → Система → Ресепшен → Врач | ФИО пациента, специалист, дата/время |
| П3 | Приём у врача и ведение медкарты | Врач → Система | Диагнозы, заключения, назначения, хронические заболевания |
| П4 | Направление и получение результатов анализов | Врач → Система → Лаборатория (API) → Система → Врач/Пациент | Направление (пациент + тип анализа), результаты анализов |
| П5 | Оплата услуг | Пациент → Кассир → ККМ → 1С:Бухгалтерия | Сумма, услуга, данные договора |
| П6 | Процессинг платежей и бухгалтерия | 1С:Бухгалтерия ↔ 1С:Торговля и склад | Суммы, номера договоров, налоговые данные |
| П7 | Уведомления пациентов | Система → Мобильное приложение / Голосовой робот → Пациент | ФИО, телефон, дата/время записи, специалист |
| П8 | Просмотр данных пациентом через ЛК | Пациент → Портал/мобильное приложение → Система | Анализы, заключения, записи, договор |
| П9 | Аналитика и отчётность (BI/ML/AI) | Система → Озеро данных → Аналитик | Обезличенные показатели, агрегированная статистика |
| П10 | Обмен данными между филиалами | Филиал A ↔ Система ↔ Филиал B | Все категории данных пациентов |

### 5.2. Меры обеспечения конфиденциальности по потокам

#### П1. Регистрация пациента

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Токенизация ПДн при вводе | **PostgreSQL** (зашифрованная БД ПДн) + **StarVault** (ключи) | ФИО, телефон, email, дата рождения токенизируются сразу при поступлении в систему. Оригиналы шифруются и сохраняются в выделенной БД ПДн. В основных БД хранятся только токены |
| Получение согласия на обработку ПДн | **Портал / приложение** | Электронное согласие (ст. 9, 10 152-ФЗ) с фиксацией факта и времени в системе. Отдельное согласие на обработку специальной категории (медицинские данные) |
| Минимизация данных | **Политика + UI** | Место работы/учёбы исключено из собираемых полей. Ранее собранные данные помечены тегом `DEPRECATED` и подлежат удалению. Адрес — только при обоснованной необходимости |
| Шифрование канала ввода | **TLS 1.2+** | Данные от браузера/приложения до бэкенда передаются по зашифрованному каналу |

#### П2. Запись к специалисту

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Токенизация пациента в записи | **PostgreSQL** (зашифрованная БД ПДн) + **StarVault** (ключи) | В таблице записей хранится токен пациента, не ФИО |
| Контроль доступа по роли | **Keycloak + OpenMetadata** | Ресепшен видит ФИО (раскрытие токена). Кассир не видит записи. Врач видит записи к себе |
| Кеширование политик | **OpenMetadata** | Политики из OpenMetadata кешируются локально в сервисах, обновляются по событию |
| Шифрование канала | **TLS 1.2+** | Все коммуникации между порталом пациента, бэкендом и хранилищами — через TLS |

#### П3. Приём у врача и ведение медкарты

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Шифрование медицинских данных at rest | **StarVault** (ключи) + **PostgreSQL** (pgcrypto) | Диагнозы, заключения, назначения шифруются при записи в БД. Ключи шифрования хранятся в StarVault |
| Физическая изоляция медицинских данных | **Архитектура хранилищ** | Медицинские данные (`PHI`, `CLINICAL`) хранятся в отдельной БД от идентификационных (`PII`) и финансовых (`FINANCIAL`) |
| БД Аудита | **OpenSearch** | Каждое обращение к медицинским данным логируется: кто, когда, к каким данным, какое действие |
| Контроль доступа | **Keycloak + OpenMetadata** | Только роль `Doctor` имеет доступ к `PHI` и `CLINICAL` |

#### П4. Интеграция с лабораторией анализов

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Токенизация пациента в API-контракте | **PostgreSQL** (зашифрованная БД ПДн) + **StarVault** (ключи) | Лаборатория получает токен пациента и тип анализа. ФИО не передаётся |
| Шифрование канала | **mTLS** (mutual TLS) | Двусторонняя аутентификация между системой «Медикаменте» и API лаборатории |
| Шифрование результатов at rest | **StarVault** (ключи) + **PostgreSQL** (pgcrypto) | Результаты шифруются при записи в хранилище медицинских данных |
| Контроль API-контрактов | **Архитектура API** | API не позволяет перебирать пациентов или получить данные чужого пациента. Доступ строго по уникальному идентификатору направления |
| Data Lineage | **OpenMetadata** | Отслеживание цепочки: `RAW` (поступление из лаборатории) → `VERIFIED` (проверка врачом) → `ANALYTICS` (обезличенные данные) |

#### П5. Оплата услуг

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Токенизация пациента в платежах | **PostgreSQL** (зашифрованная БД ПДн) + **StarVault** (ключи) | Платёж привязан к токену пациента и номеру договора, не к ФИО |
| Шифрование канала ККМ → сервер | **TLS** | Замена незащищённого TCP/IP-соединения на TLS |
| Контроль доступа кассира | **Keycloak + OpenMetadata** | Кассир видит `FINANCIAL` и минимальный набор `PII` (ФИО и номер договора) для приёма платежа и печати платёжного документа. Доступа к `PHI`, `CLINICAL` нет |

#### П6. Процессинг платежей и бухгалтерия

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Обезличивание данных для бухгалтерии | **Архитектура хранилищ** | Бухгалтерия работает с номерами договоров и суммами. ФИО пациентов не передаётся в контур бухгалтерии |
| Перевод 1С из файлового режима | **1С: клиент-серверный режим + PostgreSQL** | Клиент-серверный режим обеспечивает аудит, разграничение доступа и транзакционную целостность |
| Единый источник данных о платежах | **Архитектура** | Отказ от дублирования данных в Excel + 1С. Все платёжные данные — в 1С, передача в аналитику — через Сервис интеграции |

#### П7. Уведомления пациентов

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Раскрытие контактов только в момент отправки | **PostgreSQL** (зашифрованная БД ПДн) + **StarVault** (ключи) | Сервис уведомлений получает телефон/email по токену только в момент отправки. После отправки контактные данные не сохраняются в сервисе уведомлений |
| Минимизация данных в уведомлении | **Политика** | В тексте уведомления — только дата, время, имя специалиста. Без диагнозов, результатов анализов, полного ФИО |

#### П8. Просмотр данных пациентом через ЛК

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Аутентификация и авторизация | **Keycloak** | OAuth2/OIDC, двухфакторная аутентификация (TOTP). Пациент получает роль `Patient` |
| Изоляция данных пациента | **Архитектура API** | Пациент видит только свои данные. API не позволяет запросить данные другого пациента (привязка к ID из JWT) |
| Маскирование контактных данных | **Логика UI** | Телефон и email в ЛК показываются в маскированном виде. Полное значение — по явному действию с логированием |
| Шифрование канала | **TLS 1.2+** | Весь трафик между мобильным приложением / браузером и бэкендом — через TLS |

#### П9. Аналитика и отчётность (BI/ML/AI)

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Деидентификация данных перед загрузкой в DWH | **Batch/Export API** (в составе сервиса мед. данных) | Данные деидентифицируются на стороне источника: прямые идентификаторы (ФИО, телефон, email, адрес) удаляются, даты рождения заменяются на возрастные группы, диагнозы — на коды МКБ-10 без привязки к пациенту. ETL-сервис получает уже безопасный датасет |
| Контроль доступа аналитика | **Keycloak + OpenMetadata** | Роль `Analyst` видит только данные с тегом `ANALYTICS`. Доступ к `PII`, `PHI`, `CLINICAL`, `FINANCIAL` в необезличенном виде закрыт |
| Data Lineage | **OpenMetadata** | Отслеживание происхождения каждого датасета в DWH: из каких источников, какие трансформации применены, когда обновлялся |

#### П10. Обмен данными между филиалами

| Мера | Инструмент | Описание |
|------|-----------|----------|
| Шифрование канала между филиалами | **VPN / mTLS** | Межфилиальный обмен данными только через зашифрованный канал |
| Централизованное хранилище ключей | **StarVault** | Единый StarVault для всех филиалов. Ключи шифрования управляются централизованно |
| Единая БД токенизированных ПДн | **PostgreSQL** (зашифрованная БД ПДн) | Токены пациентов одинаковы в любом филиале — единая БД с зашифрованной репликацией |
| Единые политики доступа | **OpenMetadata + Keycloak** | Политики доступа едины для всех филиалов, управляются централизованно |
| Репликация с шифрованием | **PostgreSQL** (шифрованная репликация) | Данные между филиалами реплицируются в зашифрованном виде |
