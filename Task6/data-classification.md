## 1. Движок классификации данных перед загрузкой в DWH

### Место в архитектуре

Движок классификации встраивается в существующий ETL-пайплайн (Apache Airflow) как промежуточный шаг между извлечением данных (Extract) и загрузкой в ClickHouse (Load). Общая схема этапов: **E → Classify → T → L**.

Движок работает в двух режимах в зависимости от типа источника.

**Структурированные данные (Postgres-базы).** Схема таблиц известна, поля уже размечены тегами в каталоге OpenMetadata. Движок выполняет валидацию: сверяет текущую схему с каталогом, ловит schema drift (новые или изменённые столбцы без тегов). Если всё на месте — данные проходят дальше. Если появилось неразмеченное поле — движок пытается классифицировать его автоматически по имени столбца, типу и контексту таблицы. Если это не удаётся — поле уходит в карантин.

**Неструктурированные данные (Minio/S3).** Сканы медкарт, PDF, Excel-файлы из legacy-периода. Тут два варианта: 

1. Файл уже классифицирован (тег есть в OpenMetadata) — движок анализирует содержимое: извлекает данные (OCR для сканов, парсинг для Excel/PDF) и сразу трансформирует конфеденциальные данные.
2. Файл не классифицирован — движок анализирует содержимое: извлекает текст (OCR для сканов, парсинг для Excel/PDF), ищет конфиденциальные сущности и присваивает класс К1–К4, а затем уже трансформирует или отправляет в карантин, если не удалось классифицировать.

### Компоненты движка

**Schema Scanner** — при каждом батче проверяет схему входящих данных. Сравнивает с каталогом OpenMetadata. Если все поля размечены — данные проходят дальше без задержек. Если обнаружены новые или изменённые поля без тегов (schema drift), Scanner передаёт их в Rule-based Classifier для автоматической классификации. Для структурированных данных это работает хорошо: по имени столбца, типу данных и контексту таблицы классификатор в большинстве случаев определяет класс (например, столбец `patient_phone` типа `varchar` в таблице `patients` → К2). Параллельно отправляется алерт разработчику о необходимости разметить поле в каталоге.

**Text Extractor** — извлекает текст из неструктурированных файлов. Tesseract OCR для сканов (JPG, PDF-сканы), парсеры для Excel и текстовых PDF.

**Rule-based Classifier** — первый проход классификации на основе правил. Правила хранятся в конфигурационном файле (YAML) и включают:
- Regex-паттерны: СНИЛС, ИНН, телефоны, email, коды МКБ-10.
- Словари: справочник МКБ-10 (названия болезней), словарь русских ФИО, справочник лекарственных препаратов.

Правила маппятся на классы через каталог типов сущностей в OpenMetadata: `Диагноз → К1`, `ФИО → К2`, `Сумма платежа → К3` и т.д.

**ML Classifier** — второй проход для того, что не поймал Rule-based. Лёгкая NER-модель (spaCy или fastText) для распознавания медицинского контекста в свободном тексте. Обрабатывает только то, что не классифицировано на предыдущем шаге.

**Confidence Evaluator** — оценивает уверенность классификации. Классификаторы работают каскадом: сначала Rule-based, затем ML (только для того, что Rule-based не поймал). Для каждого элемента данных срабатывает ровно один метод. У Rule-based правил confidence задаётся статически в конфиге (например, regex для СНИЛС — 0.99, regex для кода МКБ-10 без контекста — 0.85). ML-модель возвращает вычисленную вероятность. Confidence Evaluator сравнивает score сработавшего метода с порогом (0.85). Ниже порога — данные уходят в карантин. Для неструктурированных файлов, где в одном документе могут быть разные сущности (ФИО определило regex со score 0.95, медицинский контекст определил ML со score 0.82), confidence файла в целом берётся как минимальный из найденных (0.82), поскольку надёжность определяется слабым звеном.

**Tag Writer** — записывает результат классификации в OpenMetadata через API: тег (К1/К2/К3/К4), метод классификации, confidence score, timestamp. Это обеспечивает полный Data Lineage.

**Policy Enforcer** — на основе присвоенного класса применяет трансформации: К1 — маскирование/псевдонимизация, К2 — токенизация, К3 — шифрование значений, К4 — без дополнительной обработки. Данные защищаются до загрузки в DWH (принцип Privacy by Design).

### Режим работы пайплайна

Пайплайн не останавливается целиком при обнаружении проблем — работает принцип разделения потоков. Данные, прошедшие классификацию с достаточным confidence, сразу идут в DWH. Проблемные данные (confidence ниже порога, нераспознанные файлы, неклассифицируемые поля) изолируются в карантинную зону. Data Engineer получает алерт в Grafana и разбирает карантин: вручную размечает данные, при необходимости дополняет правила в YAML-конфиге.

Принцип fail-safe: если система не уверена в классификации, данные не попадают в общедоступные слои хранилища.

## 2. Организация слоёв в аналитическом хранилище

### Слои DWH (ClickHouse)

**Raw Layer (сырой слой)** — данные в исходном виде с тегами классификации. Доступ ограничен: только Data Engineer и Security Officer. Для столбцов К1 и К2 применяется шифрование. Retention policy — 30 дней. Назначение: отладка ETL, расследование инцидентов.

**Sanitized Layer (обезличенный слой)** — основной рабочий слой для аналитики. К1-данные заменены на хеши или удалены. К2 — токенизированы (ФИО → `token_patient_123`). К3 — агрегированы (диапазоны вместо точных сумм). К4 — без изменений. Бизнес-аналитик строит отчёты на этом слое, не видя ПДн пациентов.

**Aggregated Layer (витрины)** — готовые агрегаты для BI-дашбордов (Grafana). Полностью обезличены, нет данных уровня записи — только статистика: количество приёмов по месяцам, средний чек, загрузка врачей. Доступны широкому кругу пользователей, включая руководство.

**Quarantine (карантин)** — staging-область для данных, не прошедших классификацию с достаточным confidence. Изолирована от аналитических слоёв. Data Engineer разбирает вручную, после разметки данные проходят через пайплайн повторно.

### Дополнительные меры

**RBAC на уровне ClickHouse** — роли `analyst`, `data_engineer`, `security_officer` с разными правами на слои. Интеграция с AD.

**Row-level security** — для сценариев, когда филиалы не должны видеть данные друг друга.

**Dynamic Data Masking** — реализуется через ClickHouse views с функциями маскирования (replace, substring) и RBAC. Для каждого слоя создаются views, в которых конфиденциальные столбцы заменяются на маскированные значения. Аналитик получает доступ только к view, а не к базовой таблице. 

**TTL-политики** — автоматическое удаление сырых К1-данных по истечении срока хранения.

**Аудит запросов** — все обращения к Raw и Sanitized слоям логируются в OpenSearch (БД Аудита).

## 3. Метрики эффективности классификации

### Метрики качества

**Recall на выборке** — периодически (раз в квартал) Data Engineer вручную размечает случайную выборку данных и сравнивает с результатом классификатора. Показывает, какую долю реально конфиденциальных полей система обнаруживает. Целевое значение: ≥ 0.95 для К1, ≥ 0.90 для К2.

**Precision по классам** — доля верно классифицированных полей среди всех, отнесённых к данному классу. Оценивается на той же выборке. Интерпретация зависит от класса. Низкий precision для К1 означает, что система перестраховывается — относит к К1 то, что не является медицинскими данными. Это создаёт лишнюю нагрузку на маскирование, но не создаёт угрозу безопасности. Низкий precision для К4, напротив, критичен: система ошибочно отнесла конфиденциальные данные к операционным и не применила защитные трансформации. Такие ошибки должны выявляться аудитным сканом (leak rate) и приводить к немедленному пересмотру правил классификации.

**Leak rate** — количество конфиденциальных значений, обнаруженных аудитным сканом в Sanitized-слое без маскировки. Самая важная метрика безопасности. Целевое значение: 0 для К1.

**Доля unclassified** — процент полей/файлов, которые движок не смог классифицировать (ушли в карантин). Целевое — не более 5%. Рост говорит о появлении новых типов данных.

### Метрики производительности

**Latency батча** — среднее и p95 время классификации одного батча. Важно для SLA: данные в DWH должны обновляться за ночь.

**Throughput** — количество записей/файлов, обработанных в секунду.

**Размер очереди карантина** — сколько элементов ждёт ручной проверки. Рост означает деградацию системы.

### Метрики для оптимизации

**Schema drift rate** — частота появления новых/изменённых полей. Помогает планировать обновление правил.

**Escalation rate** — как часто аудитный скан DWH находит то, что классификатор пропустил. Тренд: растёт — система деградирует, падает — улучшается.

### Как метрики помогают в оптимизации

Метрики выводятся в дашборд Grafana и анализируются Data Engineer'ом. Если precision падает — правила слишком широкие (нужно уточнить regex или добавить context_keywords). Если recall падает — появились новые паттерны данных (дополнить словари, переобучить ML-модель). Если latency растёт — масштабировать Airflow workers. Если unclassified rate растёт — поступают данные новых типов, нужно расширить справочники. Leak rate > 0 — немедленное расследование инцидента.

## 4. Масштабируемость

### Горизонтальное масштабирование ETL и классификации

Airflow уже развёрнут в Kubernetes. При росте объёма батчей — масштабирование workers через HPA (Horizontal Pod Autoscaler). Движок классификации — stateless-сервис: каждый worker обрабатывает свой батч независимо. При пятикратном росте данных (план «Медикаменте» при открытии филиалов) просто увеличивается количество workers.

Rule-based классификатор масштабируется линейно: правила лёгкие, regex и dictionary lookup занимают миллисекунды. ML-классификатор тяжелее, но при использовании fastText тоже не является узким местом.

### Масштабирование DWH (ClickHouse)

ClickHouse нативно поддерживает шардирование. При росте данных — добавляем шарды. Данные можно распределять по `branch_id` (идентификатор филиала).

### Масштабирование правил классификации

Новые филиалы могут приносить новые типы данных (другие специализации врачей — другие формы документов). Schema Scanner автоматически обнаружит новые поля и попытается их классифицировать. Если автоклассификация не справляется — поля попадут в карантин. Data Engineer дополняет правила в YAML-конфиге — без редеплоя сервисов. При значительном росте разнообразия данных — переобучение ML-модели на накопленном датасете из карантина (отдельный Airflow DAG).

### Масштабирование OpenMetadata

В качестве хранилища OpenMetadata использует СУБД PostgreSQL, которая горизонтально масштабируется.
