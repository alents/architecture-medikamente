# Отчёт: Анализ узких мест при миграции системы «Медикаменте» на микросервисную архитектуру

## 1. Введение

Компания «Медикаменте» — это медицинский центр, который сейчас работает на довольно простой IT-инфраструктуре: один физический сервер, 1С в файловом режиме, а данные пациентов хранятся в Excel-файлах и сканах на общем диске. Компания планирует расти — открывать филиалы, нанимать сотрудников и запускать новые сервисы (портал для пациентов, мобильное приложение, интеграцию с лабораторией). Для этого необходимо перейти на микросервисную архитектуру.

Чтобы оценить трудности  такой миграции, я использовал диаграмму Исикавы («рыбья кость»). Главная проблема, которую я анализирую: **«Узкие места при миграции на микросервисную архитектуру»**. Я разбил возможные причины на шесть категорий: Инфраструктура, Программное обеспечение, Интеграция, Процессы, Персонал, Данные и безопасность.


## 2. Выявленные проблемы и рекомендации

### 2.1. Инфраструктура

| Проблема | Что происходит | Что делать | Приоритет |
|----------|---------------|------------|-----------|
| Один физический сервер Windows Server — единая точка отказа | Всё крутится на одном сервере. Если он выйдет из строя, то встанет вся компания. Для микросервисов нужна распределённая инфраструктура, один сервер тут не подходит. | Перенести инфраструктуру в ЦОД или облако, где можно организовать кластер из нескольких серверов. | Критический |
| Нет отказоустойчивости и резервирования | Нет никакого плана на случай аварии (DR-план). Нет бэкапов в другой локации. Если что-то случится с сервером — данные могут быть потеряны безвозвратно. | Настроить регулярное резервное копирование, желательно в другую локацию. Написать DR-план. | Критический |
| Нет контейнеризации и оркестрации в продакшене | CTO и админ знакомы с Kubernetes, но в реальной работе контейнеры не используются. А микросервисы без контейнеров и оркестратора очень тяжело разворачивать и масштабировать. | Развернуть Kubernetes-кластер.  Контейнеризировать новые сервисы. | Высокий |
| Сервер стоит в том же здании, что и офис | Это значит, что нет нормального контроля температуры, электропитания и физического доступа к серверу. Любой инцидент в здании (пожар, затопление) может привести к потере данных. | При переносе в ЦОД эта проблема уйдёт сама. Как временная мера — поставить ИБП и ограничить доступ в серверную. | Средний |

### 2.2. Программное обеспечение

| Проблема | Что происходит | Что делать | Приоритет |
|----------|---------------|------------|-----------|
| 1С работает в файловом режиме | В файловом режиме 1С не может работать с несколькими филиалами одновременно. Каждый филиал будет видеть только свою локальную базу. | Перевести 1С в клиент-серверный режим с использованием PostgreSQL. Тогда все филиалы смогут работать с одной общей базой. | Критический |
| Данные хранятся в Excel, JPG, PDF | Нет единой базы данных. Информация о пациентах разбросана по файлам разных форматов. | Спроектировать модель данных в PostgreSQL. Провести миграцию поэтапно — с проверкой и очисткой данных на каждом шаге. | Высокий |
| У текущих систем нет API | Ни Excel-файлы, ни 1С в файловом режиме не могут общаться с другими системами через API. А для микросервисной архитектуры API — это основной способ взаимодействия. | Создать API-слой для новых сервисов. Для 1С можно написать специальный интеграционный сервис. | Высокий |
| Данные с касс попадают в локальную файловую базу 1С | Кассовые аппараты (ККТ) подключаются к компьютеру кассира через драйверы — это нормально и так и останется. Но проблема в том, что данные с касс идут в файловую базу 1С. При открытии филиалов каждая касса будет писать в свою изолированную базу. | Эта проблема решается вместе с переводом 1С в клиент-серверный режим — тогда все кассы всех филиалов будут работать с единой базой. | Критический |

### 2.3. Интеграция

| Проблема | Что происходит | Что делать | Приоритет |
|----------|---------------|------------|-----------|
| Нет контроля потоков данных между системами | Сейчас данные между системами передаются как придётся — никаких политик и правил нет. Ограничения только на уровне бизнес-процессов, а не на техническом уровне. | Развернуть API Gateway — он будет контролировать, кто и куда обращается, проверять аутентификацию и применять политики доступа. | Высокий |
| Нет интеграции с лабораторией — ручной обмен файлами | Результаты анализов приходят в виде файлов и обрабатываются вручную. Никакой автоматизации нет. | Сделать API-интеграцию с лабораторией. При этом важно учесть требования конфиденциальности — не передавать лишние ПДн в контрактах. | Высокий |
| Двойной учёт у кассиров (Excel + 1С) — рассинхронизация | Кассиры вводят данные и в Excel, и в 1С. Это приводит к расхождениям и лишней работе. | При переходе на единую систему двойной учёт нужно убрать. 1С в клиент-серверном режиме станет единственным источником данных. | Средний |
| Нет стратегии версионирования API | Компания планирует интеграции с партнёрами. Если не продумать версионирование API, то каждое изменение будет ломать существующие интеграции. | Заложить семантическое версионирование API и обратную совместимость с самого начала разработки. | Средний |

### 2.4. Процессы

| Проблема | Что происходит | Что делать | Приоритет |
|----------|---------------|------------|-----------|
| Бизнес-процессы полностью ручные и не описаны | Всё делается в ручную, ничего не задокументировано. Без описания процессов непонятно, как правильно разделить систему на микросервисы и что автоматизировать. | Описать ключевые бизнес-процессы, например, в виде BPMN-диаграмм. Это основа для проектирования границ сервисов. | Средний |
| Нет CI/CD — ПО обновляется вручную | Нет автоматических пайплайнов для сборки и деплоя. Когда микросервисов станет много, обновлять каждый руками будет просто невозможно, и это будет постоянный источник ошибок. | Настроить CI/CD (например, GitLab CI или Jenkins, Helm). Автоматизировать сборку, тесты и деплой в Kubernetes. | Высокий |
| Нет мониторинга и алертинга | Сейчас никак нельзя узнать, что система тормозит или что-то упало — пока не поступят жалобы от пользователя. В микросервисной архитектуре без мониторинга жить нельзя. | Поднять мониторинг — CTO знаком с Victoria Metrics, так что можно использовать связку Victoria Metrics + Grafana. Дополнительно развернуть Prometheus для scrape. Настроить алерты на ключевые метрики. | Высокий |
| Нет стратегии миграции данных | Непонятно, как именно переносить данные из Excel и файлового 1С в новую БД. Без чёткого плана есть большой риск потерять или испортить данные при переходе. | Составить пошаговый план: инвентаризация данных -> маппинг полей -> пилотная миграция -> проверка -> полная миграция. Обязательно предусмотреть откат. | Критический |
| Нет автоматизированного тестирования | Не налажен процесс тестирования, нет тестировщиков с навыком написания автотестов. В микросервисной архитектуре, где сервисы обновляются часто и независимо, без тестов нельзя быть уверенным, что обновление ничего не сломало. | Начать писать тесты (unit, integration, api, ui) и встроить их в CI/CD-пайплайн, чтобы они запускались автоматически при каждом изменении. | Высокий |

### 2.5. Персонал

| Проблема | Что происходит | Что делать | Приоритет |
|----------|---------------|------------|-----------|
| IT-команда из 3 человек, навык разработки только у админа | В команде CTO, администратор сети и бизнес-аналитик. Этого недостаточно для разработки микросервисов. Опыт разработки есть только у администратора  и CTO (знает Java). | Нанять бэкенд-разработчиков. Без команды разработки создать порталы, CRM, платёжный шлюз и API для лаборатории не получится. | Критический |
| Нет выделенного DevOps/SRE | Администратор сети умеет работать с Kubernetes, но он же чинит принтеры, настраивает сеть и занимается всем остальным. Когда появится кластер с микросервисами, CI/CD и мониторинг — это станет отдельной полноценной работой. | Либо полностью переключить админа на DevOps/SRE (и нанять кого-то на поддержку инфраструктуры), либо нанять отдельного специалиста. | Высокий |
| Нет специалиста по информационной безопасности | Компания работает с медицинскими персональными данными. Без человека, который разбирается в ИБ, сложно правильно настроить шифрование, контроль доступа и соответствие 152-ФЗ. | Нанять специалиста по ИБ. Это одна из первых вещей, которые нужно сделать, учитывая текущие проблемы с защитой ПДн. | Критический |
| Сотрудники могут сопротивляться переходу на новые системы | 20 административных сотрудников привыкли работать в Excel и 1С. Если просто поставить перед фактом — будет недовольство и саботаж, это замедлит миграцию. | Провести обучение. Привлекать ключевых сотрудников на этапе проектирования, чтобы они чувствовали себя участниками, а не жертвами изменений. | Средний |
| Нет системного аналитика и выделенного архитектора | CTO совмещает архитектуру с управлением, бизнес-аналитик умеет строить отчёты в Python, но не проектировать API и доменные модели. Для микросервисов нужен кто-то, кто будет заниматься именно проектированием. | Нанять системного аналитика. На этап проектирования архитектуры можно привлечь внешнего консультанта или освободить CTO от текучки. | Высокий |

### 2.6. Данные и безопасность

| Проблема | Что происходит | Что делать | Приоритет |
|----------|---------------|------------|-----------|
| ПДн хранятся без шифрования | Персональные данные пациентов лежат в открытых файлах на общем диске. Любой, кто имеет доступ к диску, может их прочитать. | Внедрить шифрование: данные на диске (encryption at rest) и при передаче по сети (TLS). | Критический |
| Нет аудита доступа к данным | Никто не знает, кто и когда открывал медицинскую карту пациента. Если случится утечка — невозможно будет понять, откуда она произошла. | Настроить логирование всех обращений к ПДн. В будущем — добавить систему обнаружения аномалий. | Критический |
| Несоответствие 152-ФЗ | Сам технический директор признаёт, что работа с персональными данными не соответствует закону. Это грозит штрафами и потерей доверия клиентов. | Провести аудит на соответствие 152-ФЗ. По сути, выполнение остальных рекомендаций из этого раздела и закроет основные нарушения. | Критический |
| Нет разграничения доступа (RBAC/ABAC) | Кроме доменной авторизации через Active Directory, никакого контроля доступа нет. Любой сотрудник может посмотреть любую медицинскую карту. | Внедрить ролевую модель доступа (RBAC). Определить, какие роли какие данные могут видеть, и настроить это в системе. | Критический |
| Нет процедуры удаления ПДн по запросу клиента | По закону пациент может попросить удалить свои данные. Сейчас непонятно, как это сделать — файлы разбросаны по папкам, могут быть копии. Гарантировать полное удаление невозможно. | В новой системе заложить механизм удаления или анонимизации данных пациента по запросу. | Высокий |


## 3. Рекомендуемая последовательность действий

### Фаза 1: Безопасность и база (1–2 месяца)
1. Нанять специалиста по ИБ.
2. Зашифровать данные пациентов (на диске и при передаче).
3. Настроить RBAC — кто к каким данным имеет доступ.
4. Включить аудит — логировать, кто обращается к ПДн.
5. Перевести 1С из файлового в клиент-серверный режим.

### Фаза 2: Инфраструктура и команда (2–4 месяца)
1. Перенести сервер в ЦОД или облако.
2. Поднять Kubernetes-кластер.
3. Настроить CI/CD-пайплайны.
4. Запустить мониторинг и алертинг.
5. Нанять разработчиков, системного аналитика, выделить DevOps/SRE.

### Фаза 3: Миграция и новые сервисы (4–8 месяцев)
1. Спроектировать модель данных и перенести данные из Excel в PostgreSQL.
2. Развернуть API Gateway.
3. Сделать MVP: портал записи для пациентов + портал для ресепшена.
4. Подключить лабораторию через API.

### Фаза 4: Развитие (8–12 месяцев)
1. Запустить мобильное приложение.
2. Подключить платёжный шлюз и CRM.
3. Сделать озеро данных для аналитики (BI/ML/AI).
4. Настроить автоматическую проверку релизов на работу с защищёнными данными.
5. Добавить обнаружение аномалий в доступе к данным.
